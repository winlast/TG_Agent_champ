# Журнал разработки (devlog)

Реальные проблемы, которые встретились при разработке, и как они решены. Материал для слайда «Ход разработки и трудности».

## Среда разработки

- **Песочница без Ollama и Telegram.** Код писался в облачной среде, где реестр моделей Ollama и `api.telegram.org` недоступны. Поэтому все внешние зависимости спрятаны за интерфейсами с двумя реализациями: `OllamaLLM`/`FakeLLM`, `OllamaEmbedder`/`HashEmbedder`, `BotHub`/`FakeHub`. Пайплайн, MCP-сервер (настоящий, через stdio), граф LangGraph и UI проверены на заглушках. Метрики и скриншоты с настоящей моделью снимаются на ноутбуке команды (`make presentation`, `make eval`). Скрипты не дают выдать результаты FakeLLM за работу модели.
- **Бот без доступа к Telegram API.** Логику `BotHub` (создание тем, цепочка forward → copy → текст, закреп и редактирование доски) проверили тестом с имитацией Bot API: `tests/test_bot.py`.

## Итерация 1 — ядро

- **Формат экспорта.** `text` бывает строкой или массивом с объектами-ссылками, длинные посты лежат в `rich_message.blocks` с пустым `text`. В форумах тема определяется только по цепочке `reply_to_message_id` до служебного `topic_created`, а «ответ» на сообщение создания темы — это не reply. Всё покрыто тестами (`tests/test_ingest.py`).
- **Серии сообщений преподавателя.** «Описание задания:», «1. …», «2. …» по отдельности бессмысленны → склейка очередей (автор, тема, ≤ 5 мин). В живом режиме неизвестно, закончил ли автор серию, поэтому добавлена пауза-дебаунс (45 с).
- **Разбор дат: найденные баги.**
  - «05.11 23:59» сначала распознавалось как время **05:11**: регулярка времени принимала точку как разделитель. Исправлено: время через точку принимается только после «в/к/до/с» и с «круглыми» минутами, а даты отбрасываются, если пересекаются со временем.
  - «Чемпионат … 30 октября с 16:00.» — время **не находилось** из-за точки в конце предложения (неверная проверка после совпадения). Нашли на демо-сценарии, добавили тест.
  - «перенесли с 30.10 на 02.11» — брался первый срок, а не целевой. Теперь из нескольких дат выбирается та, перед которой стоит «на/до/к».
  - Фолбэк на `dateparser` превращал «к 3 паре» в 3 февраля → он вызывается только при «датных» словах (месяцы, «недел…»), а результат проверяется по окну дат.

## Итерация 2 — модули варианта А

- **Chroma и два процесса.** MCP-сервер по ТЗ — отдельный процесс (stdio), а Chroma не поддерживает нескольких писателей. Решение: пишет только агент; сервер только читает (проверено: новые документы видны во втором процессе). Индекс дедлайнов синхронизируется агентом после каждого действия.
- **stdout занят протоколом MCP.** Любой `print` или лог в stdout ломает JSON-RPC, поэтому логи MCP-сервера идут только в stderr.
- **Ошибки инструментов для LLM.** Ошибки валидации (неизвестный предмет, нет такого дедлайна, неверный формат даты) возвращаются понятным текстом со списком допустимых значений, чтобы модель могла исправиться на второй попытке.
- **Tool calling маленькой модели.** Чтобы 8B-модель не сорвала действие, введены: план ожидаемых действий, проверка вызовов, 2 попытки с подсказкой «не хватает: …» и детерминированный фолбэк **через те же MCP-инструменты**. Ошибка: сначала режим `deterministic` записывался как фолбэк и портил метрику «без фолбэка». Разделили: `executor` и `fallback`.

## Итерация 3 — обновления

- **Перенос без названия предмета.** «лабу перенесли на среду» не содержит предмета. Контекст собирается из сообщения, на которое ответили, и из дедлайнов, привязанных к нему, — так кандидат на обновление находится сразу.
- **Редактирование.** Повторная классификация отредактированного сообщения; если из него уже создан дедлайн, это «кандидат из того же сообщения». Баг из тестов: при обновлении дедлайна пометка в хабе перегенерировалась и терялся маркер «✏️ отредактировано» — теперь он сохраняется.
- **Telegram не умеет пересортировать сообщения.** Доска — одно закреплённое сообщение (при переполнении 4096 символов — несколько), которое бот редактирует (`editMessageText`); ошибка «message is not modified» игнорируется.
- **Дедупликация.** Одна ЛР пишется в «общем» чате и во «флудилке». Совпадение предмета + близость дат + похожесть названий + решение LLM (`related_deadline_id`) → новый источник у существующего дедлайна вместо дубля.

## Итерация 4–5 — Telegram и интерфейс

- **Privacy mode.** По умолчанию бот в группах видит только команды. `make doctor` проверяет `can_read_all_group_messages` и подсказывает, что сделать в @BotFather (и что бота нужно удалить и добавить заново).
- **«Ложные друзья» предметов.** Алиас «физ» находился внутри «физру» → физкультура считалась физикой. Теперь проверяется целое слово против списка `not_aliases`.
- **Доверенные авторы как подстроки.** В синтетике студентка «Аня Смирнова» стала «доверенной», потому что совпала с преподавателем «Смирнова»; «Орлова» совпала с «Орлов». Имена в фикстурах развели. В README: в `trusted_authors` лучше писать имена так, как они видны в Telegram.
- **UI и прогоны с разными бэкендами.** Интерфейс сначала брал модель из конфига, а не ту, которой сделан прогон, и поиск шёл не тем эмбеддером. Теперь UI берёт бэкенд прогона из БД.
- **Автоскриншоты.** Ожидание ответа во вкладке «Спросить» зависало: первым совпадением по тексту «[1]» был скрытый элемент из истории вопросов. Ждём только видимый ответ в чате.

## Итерация 6 — оценка

- 214 синтетических сообщений в 5 чатах, 195 размеченных постов (28 % важных), включая сложные случаи: «физра», сарказм, названия команд, ответы на вопросы, дубли, переносы, редактирования.
- Бейзлайн «поиск по ключевым словам» (без LLM) на этом датасете: F1 важности 0.69, точность предмета 0.47 — ключевые слова путают «физру» с физикой и считают важным «физика — говно».

## Запуск на ноутбуке команды (30.10)

- **Ноутбук без видеокарты.** `ollama ps` показал `qwen3:8b — 6.7 GB, 100% CPU` и `bge-m3 — 1.2 GB, 100% CPU`: генерация на
  процессоре слишком медленная для демо в отведённое время. Вывод: на CPU использовать `qwen3:4b` (`make simulate-fast`),
  а экранные формы для защиты снять в тестовом режиме (FakeLLM) с явной пометкой на слайдах.
- **Отключения WSL в VS Code.** Две модели в памяти (~8 ГБ) при лимите WSL по умолчанию (половина RAM) плюс VS Code Server
  и Claude Code → «VS Code Server for WSL closed unexpectedly». Решение: лимит памяти в `.wslconfig`, одна копия Ollama,
  `keep_alive: 5m` (модели выгружаются из памяти через 5 минут простоя), запрет Claude Code трогать систему
  (`.claude/settings.json`).
- **Второй сервер Ollama.** Помощник по коду поднял ещё один Ollama на порту 11435 и прописал его в `.env`; после
  перезапуска WSL агент не находил модель («Ollama недоступна по адресу …:11435»). `make doctor` и сообщение `simulate`
  сразу показали адрес — исправили одной командой.
