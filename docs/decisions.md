# Принятые решения

ТЗ (`CLAUDE.md`) предписывает: при неоднозначности принимать разумное решение и записывать его здесь.

## Стек и версии

| # | Решение | Почему |
|---|---|---|
| 1 | Версии закреплены на актуальные стабильные (30.10.2026): langgraph 1.2.18, langchain-core 1.7.3, langchain-mcp-adapters 0.3.2, **mcp 1.30.0**, chromadb 1.5.9, rank-bm25 0.2.2, ollama 0.6.3, aiogram 3.31.0, pydantic 2.13.5, streamlit 1.66.1 | `mcp` 2.x уже вышел, но langchain-mcp-adapters 0.3.2 требует `mcp<2`, поэтому взята последняя 1.x. pydantic — версия, которую разрешил резолвер вместе с остальными пакетами |
| 2 | LLM вызывается через официальный клиент `ollama` (AsyncClient), а не через `langchain-ollama` | Прямой контроль над `think=False`, `format=<JSON Schema>`, `temperature=0`, `keep_alive` и разбором `tool_calls`. Инструменты MCP загружаются через **langchain-mcp-adapters** (как в ТЗ) и конвертируются в формат tool calling Ollama |
| 3 | JSON Schema классификации плоская, без `$ref` (`models.classification_json_schema`) | Грамматика структурированного вывода Ollama надёжнее работает с плоской схемой; Pydantic-модель `Classification` валидирует результат |
| 4 | Корень репозитория = корень проекта (без вложенной папки `study-radar/`) | Меньше шагов при запуске: `git clone → cd → make setup` |
| 5 | Python ≥ 3.11; `make setup` использует `uv`, если он есть (сам скачает Python 3.12), иначе `python3 -m venv` | В WSL с Ubuntu 22.04 системный Python 3.10 — `uv` снимает проблему одной командой |
| 6 | Добавлен пакет `tzdata` | На Windows нет системной базы часовых поясов для `zoneinfo` (`Europe/Moscow`) |

## Данные и индексация

| # | Решение | Почему |
|---|---|---|
| 7 | Документ индекса = пост (сообщение или склеенная очередь), `id = "<chat_id>:<первый message_id>"` | Идемпотентность: повторный `index --export` не плодит дубли (upsert по id, хеш текста) |
| 8 | Эмбеддинги считаем сами и передаём в Chroma; имя коллекции содержит имя эмбеддера (`messages__ollama-bge-m3`) | Смена модели эмбеддингов не ломает размерность; встроенная ONNX-модель Chroma не скачивается |
| 9 | **Chroma пишет только процесс агента**; MCP-сервер (дочерний процесс) Chroma только читает (`search_messages`). Коллекция `deadlines` синхронизируется агентом в узле `log` после каждого действия; дедупликация внутри MCP сравнивает эмбеддинги названий напрямую | Chroma не рассчитана на нескольких писателей из разных процессов. Чтение из второго процесса проверено (новые документы видны) |
| 10 | BM25 с токенизацией «первые 5 символов слова» | Простая замена стемминга для русского без лишних зависимостей: «лабу/лабы/лабораторная» → «лабу»/«лабы»/«лабор» — частично совпадают, а векторная часть добирает смысл |
| 11 | Склейка очередей идёт по потоку (чат, тема): подряд, один автор, ≤ 5 мин. Ответ (reply) на сообщение вне очереди начинает новый пост. В живом режиме бот ждёт паузу 45 с (`bursts.live_debounce_seconds`) | В живом потоке нельзя знать, закончил ли преподаватель серию; 45 с — компромисс между задержкой и склейкой |
| 12 | Время в Telegram-экспорте берётся из `date_unixtime` (если есть) и переводится в `Europe/Moscow` | Поле `date` в экспорте — локальное время компьютера, на котором делали экспорт |
| 13 | Фикстуры генерируются скриптом `scripts/make_fixtures.py`; генератор сам проверяет, что разметка совпадает со склейкой парсера | Разметка (`labeled.jsonl`) и фикстуры не разъезжаются при правках |
| 14 | Преподаватель кейс-чемпионата в синтетике — вымышленный «Громов Ю. Е.». В `trusted_authors` реальное имя оставлено для работы на настоящих чатах | ТЗ: синтетика с вымышленными именами |

## Агент

| # | Решение | Почему |
|---|---|---|
| 15 | Префильтр пропускает дальше всё, где упомянут предмет или его «ложный друг» (физра), даже короткое | «физика — это боль» должна дойти до LLM: именно на ней видно решение по смыслу (шум), а не по ключевым словам |
| 16 | Сроки: дедлайн без времени → 23:59; событие без времени → 00:00 = «время неизвестно» (на доске — только дата); перенос события без указания времени → время неизвестно | ТЗ, раздел 5.4; при переносе «на среду» прежнее время пары обычно не сохраняется |
| 17 | Дата от LLM перепроверяется правилами и dateparser от **даты сообщения**. Если день не совпал и правило «точное» (явная дата, день недели, «завтра»), берётся дата, вычисленная кодом; иначе остаётся дата LLM. В обоих случаях уверенность понижается и это пишется в журнал | Маленькие модели путаются в днях недели; «к следующей паре» правило не решает — там слово за LLM |
| 18 | `related_deadline_id` принимается только из списка кандидатов, показанных LLM | Защита от выдуманных id |
| 19 | Отредактированное сообщение, из которого уже был создан дедлайн, — кандидат «это же сообщение»; если LLM не указала связь, валидация связывает сама | ТЗ: перенос через редактирование |
| 20 | Узел `act`: по классификации строится **план** ожидаемых действий. Он нужен (а) для проверки вызовов LLM и (б) для фолбэка. LLM получает только 7 инструментов действия (`agent.act_tools`); `search_messages`/`get_message_context` доступны через MCP, но в act не нужны | Короче промпт → быстрее на CPU и меньше ошибок у 8B-модели |
| 21 | Фолбэк выполняется **через те же MCP-инструменты** (не прямыми вызовами Python) и помечается в журнале (`by: fallback`); `refresh_deadlines_board` гарантирует узел `verify` (это не считается фолбэком). Режим `act_mode: deterministic` помечается `by: executor` и в метрику фолбэков не входит | Честная метрика «доля MCP-действий без фолбэка» |
| 22 | Если LLM создала дедлайн с датой другого дня, чем после валидации, фолбэк исправляет её через `update_deadline` (история сохраняется) | Агент исправляет собственные ошибки |
| 23 | Пометку для `forward_to_topic` код готовит заранее («🗓 Дедлайн · Физика · ДЗ №3 — до чт 05.11, 23:59 · уверенность 0.92») и передаёт LLM; пометки, привязанные к дедлайну, при изменениях перегенерируются (старое значение зачёркнуто) | Единый формат пометок, предсказуемое редактирование |
| 24 | Добавлена служебная тема **«📢 Общее»** для важных сообщений без предмета (собрание группы, общежитие) | В ТЗ таких тем нет, но терять такие сообщения нельзя |
| 25 | Отмена без известного дедлайна (например, пары) — только пересылка; на доску не попадает | На доске — сроки сдачи и события, а не расписание |
| 26 | Задание без срока попадает на доску в раздел «❔ Без точного срока» | Не теряется, но не мешает сортировке |
| 27 | Отменённые события 3 дня показываются на доске зачёркнутыми, потом исчезают; прошедшие сворачиваются в «✅ Прошедшие» (`hub.past_mode`) | Видно, что изменилось, без мусора |
| 28 | Дедупликация: тот же предмет, дата в пределах ±36 ч, похожесть названий по эмбеддингам ≥ 0.82 (или совпадение) → новый источник у существующего дедлайна. Подтверждение LLM — через `related_deadline_id` | ТЗ, раздел 5.6 |
| 29 | В режиме симуляции «часы агента» = время сценария (`meta.clock_now`) | «Сегодня/Завтра» на доске считаются от сценария, скриншоты воспроизводимы |

## Telegram

| # | Решение | Почему |
|---|---|---|
| 30 | Хаб можно задать командой `/sethub` в группе (id сохраняется в SQLite) — `HUB_CHAT_ID` в `.env` необязателен | Меньше ручных шагов: не нужно узнавать id |
| 31 | Пересылка: `forwardMessage` → при запрете `copyMessage` → иначе текст + ссылка на оригинал. Удалённая тема хаба создаётся заново | ТЗ 5.6 + устойчивость |
| 32 | Главный процесс и MCP-сервер используют каждый свой экземпляр `aiogram.Bot` с одним токеном; все сообщения хаба пишутся в общую таблицу `hub_messages` | MCP-сервер — отдельный процесс (stdio) |

## Оценка и презентация

| # | Решение | Почему |
|---|---|---|
| 33 | `eval` проигрывает фикстуры **через весь пайплайн** хронологически (а не классифицирует посты по отдельности) | Честная проверка переносов, дублей и RAG-контекста |
| 34 | Для неоднозначных меток допускаются альтернативные категории (`category_alt`), например «выступить в другой день нельзя» — announcement или deadline_update | Разметка спорных случаев не должна штрафовать разумный ответ |
| 35 | По умолчанию LLM сама вызывает инструменты для первых 25 важных постов (`--act-sample`), дальше действует исполнитель | Иначе оценка на CPU занимает много часов; качество классификации измеряется на всех постах |
| 36 | Бейзлайн «ключевые слова» использует тот же разборщик дат | Сравнение честное: разница — именно в понимании смысла |
| 37 | Презентация собирается скриптом (python-pptx) из одного источника вместе с `presentation.md`; скриншоты снимает Playwright. Данные FakeLLM скрипты отклоняют | Команда тратит минимум времени; исключена подмена результатов модели |
| 38 | Схема рендерится PlantUML с `!pragma layout smetana` | Не нужен Graphviz |
