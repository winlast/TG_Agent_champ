## 0. Контекст и цель

Проект делается командой **SuperPuper** (МГТУ им. Баумана, кафедра ИУ5, группа ИУ5-31Б) для **кейс-чемпионата по созданию ИИ-агентов** (дисциплина «Архитектура АСОИУ», организатор Ю. Е. Гапанюк). Защита — презентация со скриншотами работы агента; живая демонстрация не обязательна, но проект должен реально запускаться на ноутбуке команды.

**Проблема.** У студента 5+ учебных чатов. Важное (дедлайны, задания, переносы, объявления) тонет во флуде, мемах и болтовне. Поиск по ключевым словам не работает: «физика — говно» содержит слово «физика», но не важна; «лабу перенесли на среду» вообще не содержит названия предмета.

**Что делает агент.**
1. Читает несколько учебных чатов (источники).
2. Для каждого сообщения **по смыслу** (LLM, а не по ключевым словам) решает: важно ли оно, к какому предмету относится, что это (дедлайн, задание, перенос, объявление, мусор), какой срок.
3. Пересылает важные сообщения в отдельный **чат-хаб** (супергруппа с топиками) — в топик нужного предмета, с короткой пометкой агента.
4. Ведёт топик **«📅 Дедлайны»** — одно закреплённое сообщение со всеми дедлайнами, **отсортированными по сроку**; агент **редактирует** его при каждом изменении.
5. Отслеживает **обновления**: перенос срока, отмена, уточнение (в том числе отредактированные сообщения). Находит, к какому уже известному дедлайну относится новое сообщение, и обновляет его, а не создаёт дубль.
6. Отвечает на вопросы пользователя по переписке (`/ask когда сдавать лабу по элтеху?`) со ссылками на исходные сообщения.

**Ключевая идея для защиты:** это не чатбот «спроси — ответь», а **автономный агент**: сам реагирует на события, принимает решения, вызывает инструменты и исправляет ранее внесённые данные.

## 2. Окружение разработки и ограничения

Ты, скорее всего, работаешь в облачной песочнице, а не на ноутбуке команды. В ней может **не быть** доступа к Ollama (и к загрузке моделей), к `api.telegram.org`, к HuggingFace. **Не трать время на обход сетевых ограничений.** Вместо этого:

- Все внешние зависимости — за интерфейсами с двумя реализациями:
  - `LLMClient`: `OllamaLLM` (настоящий) и `FakeLLM` (детерминированный, на правилах, **только для тестов**);
  - `Embedder`: `OllamaEmbedder` (настоящий, `bge-m3`) и `HashEmbedder` (детерминированный, только для тестов);
  - `TelegramHub`: `BotHub` (настоящий, aiogram) и `FakeHub` (пишет в SQLite и показывается в Streamlit как «чат Telegram»).
- Если Ollama в песочнице доступна — прогони всё с настоящей моделью. Если нет — убедись, что всё работает с фейками и тестами, а настоящий режим будет запущен на ноутбуке.
- **Честность:** результаты с `FakeLLM` никогда не выдавать за работу модели. Метрики качества и скриншоты для презентации — только с настоящей LLM. В README и в `docs/presentation.md` это явно оговорить.

Команда хочет **только скачать готовый проект и запустить демо**. Поэтому запуск на ноутбуке должен занимать минимум шагов (раздел 10).

## 4. Особенности учебных чатов (учти в парсере, промптах и тестах)

Это наблюдения из реального учебного чата (Telegram-экспорт кейс-чемпионата). Под них нужно настроить логику.

### 4.1. Формат Telegram JSON-экспорта (Desktop → Export chat history → JSON)

```json
{
  "name": "Название чата", "type": "private_supergroup", "id": 4361773304,
  "messages": [
    {"id": 22, "type": "service", "date": "2026-10-21T16:12:35", "action": "topic_created", "title": "Задание", "text": ""},
    {"id": 31, "type": "message", "date": "2026-10-21T16:19:32", "edited": "2026-10-21T16:24:07",
     "from": "Yuriy Gapanyuk (АСОИУ 2 сем)", "from_id": "user264928074",
     "reply_to_message_id": 22, "text": "А. Реализация всех возможностей ...", "text_entities": [...]},
    {"id": 2, "type": "message", "text": ["Вот ссылка - ", {"type": "link", "text": "https://t.me/..."}, ""]},
    {"id": 159, "type": "message", "rich_message": {"blocks": [
        {"type": "paragraph", "text": {"type": "plain", "text": "..."}},
        {"type": "list", "kind": "bullet", "items": [{"text": {"type": "plain", "text": "..."}}]}]}},
    {"id": 9, "type": "message", "file": "(File not included...)", "file_name": "RAG.pdf", "text": ""}
  ]
}
```

Обязательно обрабатывать:
- `text` бывает **строкой** или **массивом** из строк и объектов `{type, text}` — склеивать в плоский текст;
- `rich_message.blocks` (абзацы, списки) — тоже в плоский текст;
- служебные сообщения (`type: service`): `topic_created`, `pin_message`, `join_group_by_link` и т. п. Не классифицировать, но `topic_created` использовать для определения топика;
- **форумы**: топик сообщения определяется по цепочке `reply_to_message_id` до служебного `topic_created`. Сообщения без привязки — в «General». Название топика исходного чата — полезный контекст для LLM (топик «Задание» → скорее важное);
- поле `edited` — сообщение редактировали. Отредактированное важное сообщение может означать **изменение срока**;
- файлы и фото без текста: использовать `file_name` как текст (например, «RAG_и_генеративный_ИИ.pdf» в топике «Книги» → материалы курса).

### 4.2. Как пишут в учебных чатах

- **Преподаватель дробит объявление на серию коротких сообщений подряд**: «Описание задания:», затем «1. …», «2. …», «3. Возможны варианты:», «А. …», «Б. …». По отдельности они бессмысленны. → **Склейка «очередей»**: сообщения одного автора в одном чате или топике с интервалом не больше 5 минут объединяются в один логический пост перед классификацией (настраиваемо). При пересылке пересылаются все сообщения очереди.
- **Информация уточняется позже**: «Номера аудиторий будут уточняться» → через неделю «будет проходить в аудитории 501ю … 30 октября с 16:00». → Это **обновление** события, а не новое событие.
- **Сроки в свободной форме**: «30 октября (пятница) с 15:55 до 20:45», «у нас 1,5 недели до сдачи», «до пятницы», «к следующей паре», «завтра», «на этой неделе». Относительные даты считаются **от даты сообщения**, а не от текущей. Часовой пояс — `Europe/Moscow`.
- **Сроки меняются**: время «15:55» → позже «с 16:00»; «можно в другой день» → позже «выступить в другой день нельзя». Новое сообщение **отменяет** старое условие.
- **Много шума**: названия команд («Петруша», «Los Pollos Hermanos»), «спасибо», «желаем успехов», «ВСЕХ ЖДЕМ!!!», эмодзи-реакции, «а что за победу дают?», мемы, ругань на предметы.
- **Вопросы студентов** («А если команда не может 30 октября?») сами по себе не дедлайн, но **ответ** на них может быть важным → учитывать `reply_to` (подтягивать текст сообщения, на которое ответили).
- **Сленг и сокращения**: «физос» = физика, но **«физра» = физкультура**; «матан», «линал», «элтех» = электротехника, «тервер»/«ТВиМС», «АиСД»/«алгосы», «БД»/«модели данных», «АСОИУ», «лаба», «дз», «рк» (рубежный контроль), «кр», «дедлайн»/«дед», «сдача», «защита».
- Важность часто задаёт **автор** (преподаватель или староста). Настраиваемый список «доверенных авторов» в конфиге повышает приоритет, но не отменяет проверку смысла.

## 5. Архитектура

```

 │ JSON-экспорт (история)    │            │ … 📅 Дедлайны (закреп-доска)  │
 └────────────┬─────────────┘            │ 🤔 На проверку  🧾 Журнал     │
              ▼                           └──────────────▲───────────────┘

              ▼                                          │

              ▼                                   │       │
 [Префильтр (эмбеддинги, щедрый порог)]           │       │
              ▼                                   │       │

              ▼                                           │
```

### 5.1. Модуль 1 — индексация (`src/study_radar/index/`)

- Документ = нормализованное сообщение (или склеенная очередь). Метаданные: `chat_id`, `chat_title`, `topic`, `message_ids`, `author`, `date`, `edited`, `subject` (после классификации), `category`, `link`.
- Отдельная коллекция `subjects`: справочник предметов из `config/subjects.yaml` (название, алиасы, преподаватели, типичные работы) — помогает префильтру и классификатору.
- Отдельная коллекция `deadlines`: текстовое описание каждого дедлайна, для сопоставления обновлений.
- Команда `study-radar index --export path/to/result.json` загружает историю из экспорта. Идемпотентно: повторная загрузка не плодит дубли.

### 5.2. Префильтр (`agent/prefilter.py`)

Нужен только для экономии ресурсов. **Не** основа решения.
- Отбрасывать: пустые, служебные, только эмоджи и стикеры, явные «спасибо / ок / +» короче 3 слов без дат и чисел.
- Оценивать «учебность» по косинусной близости к прототипам («дедлайн по лабораторной», «перенос сдачи», «задание на дом», «аудитория и время защиты», …) и к справочнику предметов. Порог **щедрый** (лучше пропустить мусор в LLM, чем потерять дедлайн). Порог в конфиге.
- Маркеры дат, времени и чисел («до 5-го», «16:00», «пятница») всегда пропускают сообщение дальше.

### 5.3. Сбор контекста + RAG (`retrieval/`)

Для классификации каждого кандидата собрать:
- сообщение (или очередь) целиком + название чата и топика + автора + дату с днём недели;
- сообщение, на которое ответили (`reply_to`), и до 5 предыдущих сообщений в этом чате или топике за 30 минут;
- top-k похожих ранее важных сообщений (гибридный поиск);
- top-k **активных дедлайнов** — кандидатов на обновление (поиск по коллекции `deadlines` + фильтр по предмету, если он угадан);
- список предметов с алиасами.

### 5.4. LLM-классификация (`agent/classify.py`, `prompts/classify.md`)

Структурированный вывод через Ollama `format=<JSON Schema>` (или `with_structured_output`), `temperature=0`. Pydantic-схема:

```python
class Category(str, Enum):
    DEADLINE = "deadline"             # срок сдачи чего-либо
    ASSIGNMENT = "assignment"         # выдано задание (срок может отсутствовать)
    DEADLINE_UPDATE = "deadline_update"  # перенос / уточнение срока известной задачи
    CANCELLATION = "cancellation"     # отмена задания / пары / события
    EVENT = "event"                   # событие с датой/местом: защита, рк, консультация, чемпионат
    ANNOUNCEMENT = "announcement"     # важное объявление без срока (правила, требования, ссылки)
    MATERIALS = "materials"           # учебные материалы (файлы, книги, ссылки)
    NOISE = "noise"                   # не важно

class Classification(BaseModel):
    is_important: bool
    subject: str | None               # ключ из subjects.yaml или None
    category: Category
    importance: int                   # 1..5
    title: str                        # коротко: «ДЗ №3», «Защита ЛР2», «Кейс-чемпионат»
    summary: str                      # 1 предложение, что важно
    due_text: str | None              # как написано: «до пятницы 23:59»
    due_at: datetime | None           # ISO с таймзоной, вычисленная от даты сообщения
    location: str | None              # аудитория, ссылка на созвон
    related_deadline_id: int | None   # если это обновление известного дедлайна
    confidence: float                 # 0..1
    reason: str                       # короткое объяснение решения (для журнала и демо)
```

Правила промпта:
- Решать **по смыслу**. Упоминание предмета без учебной информации — `noise` («физика — говно», «кто на физру?», «матан опять скучный»).
- Сообщение без названия предмета относить к предмету по контексту (топик, reply, соседние сообщения, похожие дедлайны).
- Даты считать **от даты сообщения**. Время не указано: для дедлайна ставить 23:59, для события — по контексту, иначе `due_text` без времени. Неоднозначность — понижать `confidence`.
- Новое сообщение противоречит или уточняет известный дедлайн из контекста → `deadline_update` + `related_deadline_id`.
- 6–10 few-shot примеров прямо в промпте, включая сложные: «физра ≠ физика», перенос без названия предмета, серия сообщений преподавателя, «аудитории будут уточняться» → позже конкретная аудитория, вопрос студента + ответ преподавателя, сарказм.
- После LLM — **валидация кодом**: дата парсится и не в далёком прошлом или будущем (окно в конфиге); `subject` есть в справочнике, иначе `None` и в «🤔 На проверку»; дата из LLM перепроверяется по `due_text` через `dateparser` (с `RELATIVE_BASE` = дата сообщения, язык `ru`), при расхождении — понизить `confidence` и записать в журнал.

### 5.5. Агент и MCP (`agent/graph.py`, `mcp_server/server.py`)

**LangGraph**-граф:
`ingest → prefilter → build_context (RAG) → classify → act (LLM + MCP-инструменты) → verify → log`

- Узел `act`: LLM получает классификацию и контекст и **сама вызывает MCP-инструменты** (ReAct, tool calling Qwen3). Это и есть модуль 3, он должен реально работать через MCP, а не через прямые вызовы Python.
- Страховка для маленькой модели: если за 2 попытки LLM не сделала корректных вызовов (не тот инструмент, битые аргументы), детерминированный исполнитель применяет действие по классификации. Факт фолбэка пишется в журнал (это материал для слайда «Трудности»).
- Узел `verify`: проверить, что ожидаемые эффекты случились (сообщение переслано, дедлайн в БД, доска обновлена).

**MCP-сервер** (FastMCP, stdio), инструменты с понятными docstring и типизированными аргументами:

| Инструмент | Что делает |
|---|---|
| `forward_to_topic(subject, source_chat_id, message_ids, note)` | Переслать сообщение (очередь) в топик предмета хаба + короткая пометка агента |
| `create_deadline(subject, title, due_at, due_text, location, source_refs, kind)` | Создать дедлайн или событие; вернуть `id` |
| `update_deadline(deadline_id, due_at?, title?, location?, status?, source_ref, change_note)` | Изменить; **история изменений сохраняется** |
| `close_deadline(deadline_id, reason)` | Отмена или выполнение |
| `list_deadlines(subject?, include_past=False)` | Список активных |
| `search_messages(query, subject?, limit=5)` | Гибридный поиск по проиндексированным сообщениям (RAG) |
| `get_message_context(chat_id, message_id)` | Сообщение + reply + соседи |
| `refresh_deadlines_board()` | Перерисовать закреп-доску в «📅 Дедлайны» |
| `flag_for_review(chat_id, message_ids, reason)` | Отправить сомнительное в «🤔 На проверку» |

Реализация инструментов работает через интерфейс `TelegramHub` (настоящий или фейковый) и SQLite.

### 5.6. Чат-хаб и доска дедлайнов (`telegram/`, `board.py`)

- Хаб — супергруппа с включёнными топиками, бот — админ с правом управлять топиками. Топики предметов создаются ботом автоматически при старте, если их нет (`createForumTopic`). Маппинг `subject → message_thread_id` хранится в SQLite.
- Служебные топики: `📅 Дедлайны`, `🤔 На проверку` (низкая уверенность), `🧾 Журнал агента` (кратко: что решил и почему — для демо и отладки; включается в конфиге).
- **Пересылка**: `forwardMessage(..., message_thread_id=…)`. Если источник запрещает пересылку (protected content) — `copyMessage` или текст + ссылка на оригинал. Следом — пометка агента, например:
  `🗓 Дедлайн · Физика · ДЗ №3 — до чт 05.11, 23:59 · уверенность 0.92`
- **Обновления**: при `deadline_update` бот **редактирует** свою прежнюю пометку в топике предмета (старая дата ~~зачёркнута~~ → новая) и отвечает (reply) новым сообщением «⚠️ Перенос: …» со ссылкой на источник.
- **Доска дедлайнов**: в Telegram нельзя пересортировать сообщения, поэтому в `📅 Дедлайны` живёт **одно закреплённое сообщение**, которое бот **редактирует** (`editMessageText`) при каждом изменении. Формат:
  ```
  📅 Дедлайны (обновлено 30.10 12:40)

  🔥 Сегодня
  • 16:00 — Кейс-чемпионат ИИ-агентов (АСОИУ) · ауд. 501ю ↗
  ⏳ Завтра
  • 23:59 — ДЗ №3 (Физика) ↗
  📆 На этой неделе
  • пн 02.11 — Защита ЛР2 (Электротехника) · было: пт 30.10 ↗
  🗂 Позже
  • …
  ```
  Сортировка по `due_at`; события помечать 📌; перенесённые — «было: …»; прошедшие убираются (или сворачиваются в конце, по конфигу); «↗» — ссылка на исходное сообщение. Лимит 4096 символов: при переполнении — несколько закреплённых сообщений-страниц. Плюс команда `/deadlines` в хабе.
- **Дедупликация**: один дедлайн в нескольких чатах = один дедлайн с несколькими источниками (совпадение предмета + похожесть названия по эмбеддингам + близость дат + подтверждение LLM).

### 5.7. Модуль 2 — RAG-ответы на вопросы (`agent/ask.py`)

- `/ask <вопрос>` в хабе, вкладка «Спросить» в Streamlit, `study-radar ask "…"` в CLI.
- Пайплайн строго по схеме преподавателя: вопрос → гибридный поиск (сообщения + дедлайны) → обогащённый промпт (вопрос + контекст + инструкции + **требование ссылок**) → LLM → ответ со ссылками `[1] чат, дата, автор`. Если ответа в контексте нет — так и сказать, не выдумывать.

### 5.8. Источники сообщений

- **Основной режим — бот** (не userbot: не рискуем личным аккаунтом). Бот добавляется в чаты-источники. В @BotFather перед добавлением отключить privacy mode (`/setprivacy → Disable`), либо сделать бота админом. Если бот уже был в чате — удалить и добавить заново. Обрабатывать апдейты `message` и **`edited_message`** (повторная классификация, возможен `deadline_update`).
- Бот не видит историю до своего добавления → история подгружается из JSON-экспорта (`index --export`).
- **Режим симуляции** (`study-radar simulate --scenario data/scenarios/demo.yaml`): «проигрывает» сообщения из фикстур через весь пайплайн в `FakeHub` с настраиваемой скоростью. Работает без Telegram. В нём настоящая LLM (если доступна Ollama) или `FakeLLM` (только тесты). Основа для скриншотов, если с ботом что-то не так.

## 8. Данные для разработки и оценки

1. **Синтетические фикстуры** — 3–5 чатов в точном формате Telegram-экспорта (строковый и массивный `text`, `rich_message`, форум-топики через `topic_created`, `edited`, файлы, служебные сообщения). Всего 200–300 сообщений, из них 20–30% важных. Чаты: «ИУ5-31Б общий», «Физика ИУ5-31Б», «Элтех лабы», «Кейс-чемпионат» (форум с топиками), «Флудилка».
2. **Обязательные сценарии в фикстурах:**
   - дедлайн с явной датой; дедлайн с относительной датой («до пятницы», «к следующей паре»);
   - **перенос** без названия предмета («лабу перенесли на среду») в ответ на сообщение о лабе;
   - **перенос через редактирование** сообщения (`edited`);
   - отмена («пары по ТВиМС завтра не будет»);
   - серия коротких сообщений преподавателя (склейка);
   - «аудитории уточняются» → позже конкретная аудитория (обновление события);
   - один дедлайн в двух разных чатах (дедупликация);
   - шум: «физика — говно», «кто на физру?», «спасибо», названия команд, мемы, сарказм;
   - вопрос студента + ответ преподавателя с важной информацией;
   - файл-материал без текста.
3. **`data/eval/labeled.jsonl`** — 120–150 размеченных примеров (`is_important`, `subject`, `category`, `due_at`).
4. **`study-radar eval`** считает precision / recall / F1 по важности, accuracy по предмету и категории, точность дат (совпадение дня), долю корректных MCP-вызовов без фолбэка, среднюю задержку на сообщение. Результат — `docs/eval_report.md` с моделью и железом в шапке. Отдельно — сравнение с **бейзлайном «поиск по ключевым словам»**, чтобы на слайде было видно, зачем LLM.

## 9. Интерфейс для демо (Streamlit, `make ui`)

Вкладки:
1. **Лента** — входящие сообщения из всех источников; рядом решение агента (бейдж категории, предмет, уверенность, `reason`), цвет: важное / шум / на проверку.
2. **Хаб** — в режиме `FakeHub` отрисовка «как в Telegram»: список топиков, в каждом пересланные сообщения с пометками агента.
3. **Дедлайны** — таблица, отсортированная по сроку, с историей изменений (было → стало, по какому сообщению).
4. **Трассировка агента** — по выбранному сообщению: найденный RAG-контекст, промпт, JSON-классификация, **последовательность MCP-вызовов с аргументами и результатами**, фолбэк. Главный экран для слайда про архитектуру.
5. **Спросить** — RAG-чат со ссылками на источники.
6. **Метрики** — результаты `eval`.

Интерфейс на русском, аккуратный, без лишнего.

## 14. Стиль кода

Типизация везде, Pydantic для границ модулей, асинхронность там, где Telegram и I/O. Логирование через `logging` (уровень в конфиге). Без лишних абстракций и «на будущее». Комментарии и докстринги — по-русски или по-английски, единообразно. Каждый модуль варианта А легко найти по имени папки — преподаватель будет смотреть код.
